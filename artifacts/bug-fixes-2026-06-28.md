## 1. "Refresh token is required." Snackbar on Owner Dashboard Load

### Symptom

When an already-onboarded owner opened the Owner Dashboard, two things happened simultaneously:

1. The **"Connect Your Stripe Account"** onboarding banner appeared — even though the owner had already completed Stripe onboarding.
2. A red snackbar error appeared: **"Refresh token is required."**

This happened on every dashboard visit, not just after returning from Stripe.

---

### Root Cause

The owner dashboard's `OwnerOverviewTabComponent` was calling `authService.refreshToken()` silently on every load when `isOnboarded()` returned `false`.

```typescript
// What was happening (WRONG)
} else if (!this.isOnboarded()) {
  this.authService.refreshToken()   // ← called silently to sync isOwnerVerified
    .pipe(takeUntilDestroyed(this.destroyRef))
    .subscribe();
}
```

`refreshToken()` internally calls:

```typescript
// AuthService.refreshToken()
this.http.post(`/api/v1/auth/refresh-token`, {}, { withCredentials: true })
```

This endpoint requires an **HttpOnly refresh-token cookie** that the browser sends automatically. That cookie is only written at login time and has its own expiry. In any of these common situations the cookie is absent:

- The session cookie expired since last login
- The owner cleared browser cookies / used Incognito
- The owner logged in on a different device or browser

Without the cookie, the backend returns `HTTP 400` with body `"Refresh token is required."` The error interceptor catches any non-401 response and shows it as a Material snackbar — so the owner saw the error on every visit.

Additionally, `isOnboarded()` was reading from `currentUser()`, which comes from `localStorage`. The JWT in localStorage was issued at login time **before** the Stripe webhook set `IsOwnerVerified = true` in the database. So even a successfully-onboarded owner had stale `isOwnerVerified: false` in their cached profile — making `isOnboarded()` always return `false` on the next login session, even though the DB had the correct value.

**Root cause chain:**

```
Owner completes Stripe → webhook fires → DB: IsOwnerVerified = true
But: JWT in localStorage still says isOwnerVerified: false  (issued before webhook)
→ isOnboarded() returns false
→ component silently calls refreshToken()
→ refresh-token cookie may be absent
→ backend returns 400 "Refresh token is required."
→ error interceptor shows snackbar
→ isOnboarded() never updates → Stripe banner stays visible
```

---

### Fix

**Backend — new lightweight profile endpoint (JWT Bearer only, no cookie):**

Added `GET /api/v1/users/me/profile` that reads `IsKycVerified` and `IsOwnerVerified` directly from the database using only the Authorization Bearer token.

```csharp
// DTOs/Users/UserProfileResponse.cs
public record UserProfileResponse
{
    public bool IsKycVerified  { get; init; }
    public bool IsOwnerVerified { get; init; }
}

// UserService.cs
public async Task<UserProfileResponse> GetProfileAsync(Guid userId, CancellationToken ct = default)
{
    var user = await _userRepo.GetByIdAsync(userId)
        ?? throw new NotFoundException("User", userId);
    return new UserProfileResponse
    {
        IsKycVerified   = user.IsKycVerified,
        IsOwnerVerified = user.IsOwnerVerified,
    };
}

// UsersController.cs
[HttpGet("me/profile")]
public async Task<ActionResult<ApiResponse<UserProfileResponse>>> GetProfile(CancellationToken ct)
{
    var profile = await _userService.GetProfileAsync(User.GetUserId(), ct);
    return Ok(new ApiResponse<UserProfileResponse> { Data = profile });
}
```

**Frontend — `UserService` and `AuthService`:**

Added `getProfile()` to `UserService`:

```typescript
// core/services/user.service.ts
getProfile(): Observable<ApiResponse<{ isKycVerified: boolean; isOwnerVerified: boolean }>> {
  return this.http.get<...>(`${this.baseUrl}/me/profile`);
}
```

Added `syncProfile()` to `AuthService`. This method calls the new endpoint (JWT only — no cookie required) and patches just the verification flags into the `currentUser` signal and localStorage, without touching the JWT itself or requiring a cookie:

```typescript
// core/services/auth.service.ts
syncProfile(): Observable<ApiResponse<{ isKycVerified: boolean; isOwnerVerified: boolean }>> {
  return this.userService.getProfile().pipe(
    tap(res => {
      if (res.success && res.data) {
        const current = this.currentUser();
        if (current) {
          const updated = {
            ...current,
            isKycVerified:   res.data.isKycVerified,
            isOwnerVerified: res.data.isOwnerVerified,
          };
          this.tokenService.setUser(updated);
          this.currentUser.set(updated);   // signal updates → isOnboarded() recomputes
        }
      }
    })
  );
}
```

**Frontend — `OwnerOverviewTabComponent`:**

Replaced `refreshToken()` with `syncProfile()` in all code paths:

```typescript
// owner-overview-tab.component.ts
ngOnInit(): void {
  const cb = this.route.snapshot.queryParamMap.get('stripeCallback');

  if (cb === 'onboarding' || cb === 'refresh') {
    // Owner just came back from Stripe — show visible spinner while syncing
    this.stripeCallbackState.set('checking');
    this.authService.syncProfile()
      .pipe(takeUntilDestroyed(this.destroyRef))
      .subscribe({
        next: () => this.stripeCallbackState.set('done'),
        error: () => this.stripeCallbackState.set('none'),
      });

  } else if (!this.isOnboarded()) {
    // Silent sync — fixes stale isOwnerVerified in localStorage
    // Uses JWT bearer token only, no cookie needed → will never show an error
    this.authService.syncProfile()
      .pipe(takeUntilDestroyed(this.destroyRef))
      .subscribe();
  }
}
```

The critical distinction:

| | `refreshToken()` | `syncProfile()` |
|---|---|---|
| Requires | HttpOnly refresh-token cookie | JWT Bearer token (always present if logged in) |
| Returns | Full new JWT with updated roles | Only `{ isKycVerified, isOwnerVerified }` |
| Can show error | Yes — 400 if cookie missing | No — user is already authenticated |
| Correct use case | After a role change (`become-owner`) | Syncing verification flags from DB |

## 2. Property Ownership Document — "Cannot GET /uploads/..." When Clicking View

### Symptom

After uploading an ownership/deed document during property creation or editing, clicking the **View** icon button next to the uploaded document opened a browser tab showing:

```
Cannot GET /uploads/properties/7691d789-f05d-4ca2-a79c-3d1f768e87ce/documents/ebab73fc-c3d0-4759-8623-699c7ed53c5b.pdf
```

The document could not be opened at all.

---

### Root Cause

**"Cannot GET"** is a Node/Express-style error message. It was coming from the **Angular dev server** (`localhost:4200`), not the ASP.NET backend (`localhost:5000`).

The backend stores file paths as **relative URLs**: `/uploads/properties/{propertyId}/documents/{fileId}.pdf`

The template bound this relative URL directly into an `href`:

```html
<!-- property-create.component.html (WRONG) -->
<a [href]="doc.documentUrl" target="_blank" mat-icon-button>
```

When a browser sees a relative URL in `href`, it resolves it against the **current page's origin**. Since the user is on `http://localhost:4200/...`, the browser navigated to:

```
http://localhost:4200/uploads/properties/.../....pdf
```

The Angular dev server has no route for `/uploads/...`, so it returned its own "Cannot GET" 404 response.

The actual file lives on the ASP.NET backend at:

```
http://localhost:5000/uploads/properties/.../....pdf
```

which is served by the `UseStaticFiles` middleware configured in `Program.cs`:

```csharp
app.UseStaticFiles(new StaticFileOptions
{
    FileProvider = new PhysicalFileProvider(
        Path.Combine(app.Environment.ContentRootPath, "uploads")),
    RequestPath = "/uploads"
});
```

This was already working for property images — they used the `imageUrl()` helper in `PropertyService` which correctly prepends the API origin. The document view link simply missed this step.

---

### Fix

**Refactored `imageUrl()` into a more general `fileUrl()` method in `PropertyService`**, then delegated `imageUrl()` to it:

```typescript
// core/services/property.service.ts

imageUrl(path: string | null): string {
  return this.fileUrl(path);  // delegates — no behaviour change for existing image usages
}

fileUrl(path: string | null): string {
  if (!path) return '';
  if (path.startsWith('http')) return path;              // already absolute — leave it
  const base = environment.apiUrl || 'http://localhost:5118';
  return path.startsWith('/') ? `${base}${path}` : `${base}/${path}`;
}
```

**Updated both templates** to use `propSvc.fileUrl()` for document view links:

```html
<!-- property-create.component.html (FIXED) -->
<a [href]="propSvc.fileUrl(doc.documentUrl)" target="_blank" mat-icon-button>

<!-- property-edit.component.html (FIXED) -->
<a [href]="propSvc.fileUrl(doc.documentUrl)" target="_blank" mat-icon-button>
```

With this fix, `doc.documentUrl = "/uploads/.../file.pdf"` becomes `"http://localhost:5000/uploads/.../file.pdf"` — the correct origin where the static file middleware serves the file.

---

### Why Images Already Worked

Property images used `propSvc.imageUrl(img.image)` which already prepended `environment.apiUrl`. Documents used `doc.documentUrl` raw. Both came from the same backend storage service (`LocalFileStorageService`) returning the same `/uploads/...` relative path — the only difference was whether the frontend prepended the API origin before using the URL.
